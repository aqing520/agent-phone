# Codex 发送入口验证

验证日期：2026-11-04。目标是手机对 Mac 上的原有会话发送消息，不将“命令退出成功”视为“智能体已执行”。

## 首版实现结果（优先于下面的初始调研）

用户已选择“先做 CLI 续接，手机能发能看即可”，不要求首版与桌面实时同步。

- 独立进程按已安装插件的 MCP 协议连接桌面 app-tools 时，连接关闭，不能复用聊天中的桌面工具。因此首版不依赖该连接，不保存聊天工具的 pipe 或调用上下文。
- 对桌面测试会话执行 `codex exec resume` 被 `active writer` 锁拒绝。空闲状态并不代表桌面释放了写入权，不会强行接管。
- 已创建独立 CLI 测试会话，CLI 续接成功；通过 `POST /api/send` 执行后返回原会话，现有 `/api/messages` 可读到回复。
- 已实现浏览器输入框、执行状态、原请求编号重试、切换会话保留草稿、明确失败时恢复输入、未支持客户端禁用输入。
- 任务保存在仓库外的私有 SQLite 中，worker 为独立进程。真实浏览器测试在服务端受理后丢弃 HTTP 回执，再重启网关、携带原编号重试，数据库中仍只有一个对应任务，回复正常显示。
- 已验证手机私人通道对应的云端入口能访问新控制接口和页面。用户在手机刷新页面即可使用。
- 请求通过 Host、Origin、JSON 类型、CSRF 令牌、会话与长度检查；不将用户消息拼入 shell 命令，CLI 消息从 stdin 输入。
- 只读会话保持只读，其他会话限制到 `workspace-write`，审批策略为 `never`：需要额外授权的操作不会在手机自动放行，首版没有审批按钮。
- WorkBuddy、DeepSeek Harness 仍保留能力入口，但尚未实现发送。

接口、运行方式与边界见 [README](../README.md#发送消息codex-cli-续接)。下文保留首轮入口调研过程。

## 本机环境

- PATH 中的 Codex CLI：`0.166.0`。
- 桌面应用自带的 CLI：`0.166.0-alpha.5.1`。
- 桌面应用运行自己的 stdio app-server。
- `codex app-server daemon version` 检查失败：默认共享 daemon 的控制 socket 不存在。桌面 app-server 与 CLI 共享 daemon 不能直接视为同一个服务。

## 实测结果

用户专门创建了测试会话，以下操作仅针对这个会话，没有向其他工作会话投递测试消息。

| 路径 | 实测结果 | 可以证明什么 |
| --- | --- | --- |
| `codex queue --thread <id> --message <text>` | 退出码 0，返回队列条目 ID；条目在队列中，但空闲桌面会话未自动执行，rollout 没有测试回复 | 支持入队，不能认定已执行 |
| 同一命令加 `--resume` | 退出码仍为 0，同时警告需要启动本地 daemon 或指定远程服务；消息仍留在队列 | 退出码不能单独判断是否成功恢复或执行 |
| 桌面 app-tools 的 `send_message_to_thread` | 接受消息，原会话约 3 秒完成，返回预期的固定测试文字，没有执行工具 | 已验证桌面会话的实际发送和回复 |
| 现有 `/api/messages` 读取测试会话 | 能读到上述桌面回复 | 现有只读链路可展示这种发送路径产生的回复 |

两条未消费的 CLI 测试消息已通过 app-server 的 `thread/queue/delete` 撤回；没有直接修改队列数据库。

另外在临时 `CODEX_HOME` 中做了无模型调用的隔离测试：仅 `thread/start`、尚未有真实持久化历史的会话，不能直接通过独立 CLI 队列读取到。因此集成测试不能仅创建一个空会话就认定跨进程发送可用。

## 官方接口与集成边界

- CLI 提供 `codex queue`，`--resume` 恢复失败也可能仅警告并成功退出，见 [官方命令说明](https://learn.chatgpt.com/docs/developer-commands)。
- App Server 有 `thread/resume`、`turn/start`、`turn/steer`、状态通知与审批协议，见 [官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)。需要连接实际拥有目标运行会话的服务。
- 本机 CLI 生成的实验性协议 schema 还包含 `thread/queue/add`、`list`、`delete`、`start` 等方法。它们应按当前安装版本探测，不能只依据某个历史接口名称。
- 聊天内能调用的桌面 app-tools 不等于独立 Python 网关天然拥有同样能力。本机插件需要桌面提供的连接及调用上下文；不能将本次工具测试当成已部署的后台桥接。
- 不应默认用另起一个 `codex exec resume` 进程接管正在工作的桌面会话，其并发行为与权限处理尚未验证。

## 初始后续实现顺序（首版已按 CLI 路线实现）

1. 确认独立网关到目标桌面运行时的连接方式，包括桌面重启后的重新发现，避免依赖只在当前聊天里存在的连接上下文。
2. 提供统一的控制适配器接口，Codex、WorkBuddy、DeepSeek Harness 各自实现能力检测、发送与状态查询。
3. 为 `POST /api/send` 增加来源/会话校验、重复请求控制和明确错误反馈；不接受任意 shell 命令。
4. 发送状态区分“已受理 / 已排队 / 执行中 / 等待审批 / 已完成 / 失败”，以实际运行时或回执为准，不能只看 CLI 退出码。
5. 在测试会话验证空闲发送、忙碌时排队或引导、审批、桌面关闭、重启重连，再接手机输入框。

上述首轮调研时尚未修改发送按钮。当前已实现 CLI 发送，但交互式审批、忙碌时排队/引导、桌面实时桥接仍待后续处理。

## 其他客户端仍在范围内

WorkBuddy、DeepSeek Harness 的发送入口分别核实，不能因当前先验证 Codex 而视为取消。对它们先检查可用 CLI、官方接口或本机运行时连接；无可靠入口时应展示明确的不支持原因，不伪造发送成功。
